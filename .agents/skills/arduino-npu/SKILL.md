# Run on the Ventuno Q NPU

Read [AGENTS.md](../../../AGENTS.md), then the NPU parts of the [MobileNet](../../../examples/standalone-litert/README.md#4-optional-run-on-the-npu-ventuno-q), [Gemma](../../../examples/standalone-litert-lm-npu/README.md), and [embedding](../../../examples/standalone-embedding/README.md#4-optional-run-on-the-npu) READMEs, plus `scripts/setup_npu.py` and `scripts/npu_runtime.py`. For source-only work, skip board operations and downloads; leave NPU verification pending.

1. Scope: Ventuno Q only (Qualcomm QCS8275, Hexagon v75). Before hardware work, read `/sys/devices/soc0/machine` (expect `QCS8275`) and confirm `/dev/fastrpc-cdsp` is accessible, which needs the account to be in the `fastrpc` group. Other boards, including Uno Q, have no NPU path here: stop rather than improvise one. Never change device permissions or groups yourself.
2. Setup is one script: `python3 scripts/setup_npu.py`. It needs no `sudo` and downloads about 170 MB into the git-ignored `npu/`: Qualcomm's libraries from Qualcomm, a LiteRT-LM runtime bundle from a pinned release of the flutter_edge_ai project, and `libatomic` through `apt-get download`, all SHA-256 verified. If it seems to need `sudo`, a different source, or a changed hash, stop and ask. Never commit `npu/` or Qualcomm binaries, and never edit a pin to accept a failing download.
3. Two mechanisms reach the same NPU; do not mix them. LiteRT-LM models (Gemma, EmbeddingGemma) are compiled ahead of time for the chip and run through LiteRT's Qualcomm dispatch library: `lm.Backend.NPU(litert_dispatch_lib_dir=...)`. A classic `.tflite` model runs through Qualcomm's delegate, which compiles it at load time: `load_delegate("libQnnTFLiteDelegate.so", {"backend_type": "htp", "htp_performance_mode": "2"})` passed as `experimental_delegates`.
4. The model and libraries must agree. A LiteRT-LM NPU file embeds the QAIRT version it was compiled with, and the downloaded libraries must be that version (currently 2.50.0.260828). Read the version from the model (`grep -a -o -E '2\.[0-9]{2}\.0\.[0-9]{6}' model.litertlm`) instead of guessing. Use the file built for QCS8275: the CPU files contain no NPU graphs, and Android/SM8750 files and libraries do not apply to this Linux setup.
5. Check what each model supports on this NPU before promising a modality. Gemma text, image, and audio all ran on the NPU with `litert-lm-api==0.18.0`; 0.17.1 failed for audio. EmbeddingGemma 2 runs text and images on this NPU; its model card lists audio as unsupported, and the NPU build will not start unless audio is given the CPU backend.
6. Prove NPU use; never assume it. The examples print `NPU evidence:` (the Qualcomm library is loaded, the NPU channel is open, and the NPU's interrupt count rose) and fail without it. Keep that check. A loaded model, a registered accelerator, or a discovery log is not evidence: a CPU model given the NPU backend still answers, on the CPU, and only the check catches it.
7. Speed claims need care. The Gemma example swaps in the bundle's LiteRT-LM library because the pip wheel leaves the NPU in its default power mode (about 3x slower in our runs). That swap uses the wheel's private internals, so keep `litert-lm-api` pinned exactly. The MobileNet example sets the high-performance mode with a delegate option, and the embedding example showed no gain from the swap. Report load time, warm-up, and steady-state separately; single runs on one board are not benchmarks.
8. Keep the CPU defaults working and unchanged; the NPU is an opt-in flag or example. The native libraries print hundreds of lines (including shutdown messages about memory handles that were harmless when the answer and exit status were good). `npu_runtime.py` sends them to `npu/last-run.log` and shows the tail on failure; do not hide a real error behind that redirect.
9. When hardware testing is authorized, run each example's NPU smoke check (`--backend npu --check` for MobileNet and embeddings; the default run for Gemma) and record the command, pinned versions, output, evidence line, exit status, and limitations. Use [debugging](../arduino-debug/SKILL.md) for failures and [documentation lookup](../arduino-docs/SKILL.md) for versions and sources.
